           第二部分　整合主稿：产品与玩法设计
             5　产品定位与核心循环
           核心幻想：「和好友一起，在会倾听的黑暗里求生。」
           三根体验支柱——被倾听的恐惧（声音即风险）、协作的必要性（分工与互救）、失控边缘的挣扎（理
           智系统）。与支柱无关的功能一律砍掉。
           核心循环：组队进入闹鬼场所 → 探索收集证据与物资 → 怪物被声音唤醒并索敌 → 躲藏 / 转移 / 利用
           道具周旋 → 达成目标后撤离 → 结算货币解锁装备与地图 → 下一局。单局 10~15 分钟（移动端碎片场
           景适配），失败惩罚为当局收益折半而非清零。

          13.4　网络同步
          Fusion Shared Mode（Host = 房主客户端，无专用服务器）。固定 60 Tick/s，每 3 Tick（50ms）一

          13.5　语音链路：判定与传输解耦
          声纹强度判定完全在本地（麦克风电平 → 相对分层 → StimulusEvent → RPC 广播至 Host 权威
          端）；语音传输层只负责「让队友听见」。收益：语音供应商成为可替换纯传输件（3~4 天切换 EOS
          Voice）；轮盘与语音玩家共用同一条判定管线；判定延迟与网络状况无关。
          唯一采集源（V8 N1，M0 W1 真机验证）：Android 上带 AEC 的 VOIP 采集会独占 AudioRecord，二
          次采集常被拒或返回静音。采集源优先级：① Vivox 本地参与者音频能量 / 电平回调（首选，零额外采
          集）；② Vivox external audio input，由 Unity 侧单一 AudioRecord 供流；③ 均不可用退化为「轮
          盘驱动声纹 + 语音纯传输」双轨。第 1 周用 2~3 台真机（高通 / 天玑 / 低端各一）交叉验证，写入 M0
          验收。

             17　开发范式总纲
           17.1　范式定义

           V5 的铁律是「人类写接口与测试，AI 生成实现」。手机模式下人类不再亲写，铁律改写为门禁制：
             规格书（AI 起草 + 人类批准）
               ├─ 接口契约（INetService 等的方法签名草稿）——人类逐行批准后才允许实现
               ├─ 验收测试意图（测什么、边界在哪）——人类批准测试清单后才允许写实现
               └─ 实现开始
           人类批准的是「契约」，AI 执行的是「实现」——架构决策权仍在人（V5 铁律的精神内核不变），只
           是从「亲写」变为「批准」。接口与测试一旦批准即冻结，实现阶段不得擅自修改；确需修改回到门
           禁重审。

             四版 157 页的演进沉淀了三样东西：一个机制层真创新的玩法（声纹即风险）、一套验证过的零成本

             设计的对象。
             手机 + AI 编程不是这套方案的妥协，恰是它的一致延伸：一个把「AI 只产出可被一次性替换的模块」
             写进铁律的方案，最终自然走向「人类只做决策与验收」。第 1 周的三重验证（麦克风、跨机一致、
             工具链）将用最便宜的方式回答这个模式是否成立——先花一周证伪开发模式与核心机制，再花十周做
             游戏。
             最坏的情况从来不是没钱，而是花 24 周做完文档里的每一条，却发现开发方式与核心机制在真机上不
             成立。所以：第 1 周，拿起手机，让 AI 写下第一行代码，然后对着它说一句悄悄话——看它是否真的
             听见了。
