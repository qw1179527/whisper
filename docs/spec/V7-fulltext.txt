          2.3　V7 新发现问题诊断（按严重度排序）
            P0-A　语音通道商用许可误判——V5 表 4-1 的免费假设不成立
            V5.0 表 4-1 声称「Photon Voice 2 免费档：随 Photon 账号（含 AEC 回声消除）」，V6.0 §12.1 沿用了该链
            路。经 2026 年 10 月复核 Photon 官方定价：Photon Voice 免费档仅 20 CCU 且明确限定「development /
            non-commercial use」（开发与非商业用途），不可用于发行的游戏；商用最低档为 100 CCU 一次性 95 美
            元 / 12 个月，500 CCU 为 95 美元 / 月。语音是本作的核心生存机制（声纹系统的物理载体），若按 V5 假设走
            到上架，将在商业化环节被许可条款直接卡死。
            修正：语音通道整体切换至  Unity Vivox——每月前 5,000 峰值并发用户（PCU）免费（标准定价，按月重
            置），含 3D 位置音频、回声消除、跨平台与 Unity 官方 SDK。本作 EA 期联机容量 100 CCU，语音并发远低于
            5,000 PCU，语音成本归零。同时重新设计语音链路架构：将「声纹强度判定」（本地麦克风电平）与「语音传
            输」（Vivox）解耦，使传输层可在 Vivox / EOS Voice 之间替换而不触碰核心机制（详见 §3.4）。备胎：Epic
            Online Services Voice（完全免费，无并发上限）。

            P0-B　后端域整体空白——权益、支付、封禁、举报全部缺少服务端设计
            V5/V6 的「后端」仅覆盖观测层（Firebase 崩溃 / 埋点 / 远程配置 / 分发）。但 V6.0 引入的三个核心系统都隐
            含了尚不存在的服务端能力：① 房主买断制（P0-1）需要服务端验证 Google Play 购买票据并下发权益——纯
            客户端判断会被破解版绕过，且 Google Play 政策明确要求服务端验证购买；② 语音合规的举报与家长控制
            （P0-3）需要举报数据落库与处理工作流；③ 最小反作弊（P0-4）的「云端标记表」「事后封禁」需要服务端
            信誉数据与封禁执行链路。此外，破解客户端会连接 AppId 消耗 CCU（见 P1-D），其防护同样依赖服务端签发
            的认证令牌。
            修正：新增本方案第四部分「后端设计全案」（§9~§15）与第五部分「后端设计提示词库」，以「最小后
            端」哲学补齐六个服务端能力：匿名身份、权益验证、封禁、举报、全局计数、遥测聚合——全部运行在
            Firebase 免费额度内。
            P0-C　CCU→DAU 容量换算偏乐观 25%~50%，且免费档规则未澄清
            V5.0 §4.8 称「100 CCU 可支撑日活 2500~3000」。Photon 官方经验法则是 CCU × 20 ≈ DAU（100 CCU ≈
            2,000 DAU / 约 40,000 MAU）。V5 的估算高出了 25%~50%，直接影响：溢出预案的触发时点、商业化目标
            （V5 §8.2 公测注册 3000+）与免费档溢出 UI（V6 §7.3）的部署里程碑。同时三条免费档规则 V5/V6 均未记
            录：① 100 CCU 是硬上限且无 Burst——超出即拒入，付费档才有 48 小时升级缓冲；② 计费峰值为「各区域
            月峰值的求和」——时区分离的多区域受众会推高有效峰值（本作发行覆盖亚欧美，受此规则影响明显）；③
            免费档一工作室限一个应用，且升级付费后不能降回免费档——「临时升级扛破圈日再降回来」不可行，必须
            按长期成本决策。
            修正：容量基线校准为 DAU 2,000（§3.5）；溢出感知实现从 M2 提前到 M1 末（§14.1，并补上 V6 §7.3 缺
            失的数据源实现路径）；付费升级决策改为阈值触发的单向门（§3.6 迁移梯队）。
            P1-D　破解客户端消耗 CCU 与流量——免费档的唯一「刺客」无防护
            Photon 官方 FAQ 明确：盗版 / 破解客户端会照常连接你的 AppId，全额消耗 CCU 与流量。本作采用 APK 先行
            通道（V5 §8.1），重打包盗版风险客观存在——100 CCU 的免费额度若被盗版客户端挤占，正版玩家将最先被
            拒入。官方防护方案为 Custom Authentication（配置认证提供方后关闭匿名连接）。本作原本无账号体系，因
            此该防护必须由后端补位：Firebase Auth 匿名账号 → Cloud Function 签发 Photon 认证令牌 → 关闭匿名连接
            （设计见 §10.2）。这同时赋予了下发封禁的能力（P0-B 的第三个子需求）。
            P1-E　Firebase Spark 免费档的 fail-closed 行为未治理
            Spark 计划超配额的行为是当月直接停用该产品（fail-closed），而非限流——若玩家数据写入 Firestore 超过
            每日 2 万次写，整个 Firestore 服务当月冻结，云存档 / 权益查询 / 封禁表全部失效，等于线上事故。V5「日均
            5 万事件内宽裕」的说法混淆了 Firebase Analytics（真免费、随 GA4 无上限）与 Firestore（有严格日配额）
            两类服务。此外 Cloud Functions 不在 Spark 内（需 Blaze 按量计划，绑卡但量内为 0 美元）——而支付验证
            （P0-B）离不开云函数，这一决策 V5/V6 均未做出。

          11.2　服务端验证函数（核心代码契约）
           // functions/src/verifyPurchase.ts —— 规格书见第五部分 P-B3
           export const verifyPurchase = onCall(async (req) => {
             const uid = req.auth?.uid;                    // 强制已登录
             const { purchaseToken, productId } = req.data;
             if (!uid || !purchaseToken || productId !== "host_unlock")
               throw new HttpsError("invalid-argument", "bad request");
             // 1. 幂等：票据已处理则直接返回（全局去重）
             const existing = await db.doc(`entitlements/${purchaseToken}`).get();
             if (existing.exists) return { status: "already_owned", ... };
             // 2. 官方验证：Play Developer API（服务账号凭据）
             const res = await publisher.purchases.products.get({
               packageName: PACKAGE, productId: "host_unlock", token: purchaseToken,
             });
             if (res.data.purchaseState !== 0)              // 0 = PURCHASED
               throw new HttpsError("failed-precondition", "not purchased");
             // 3. 归属校验：obfuscatedAccountId 必须匹配当前 uid（防票据移植）
             if (decryptObfuscated(res.data.obfuscatedExternalAccountId) !== uid)
               throw new HttpsError("permission-denied", "token mismatch");
             // 4. 权益写入（事务：票据文档 + 玩家权益标记）
             await db.runTransaction(async (tx) => {
               tx.set(db.doc(`entitlements/${purchaseToken}`),
                 { uid, productId, purchasedAt: FieldValue.serverTimestamp(),
                   orderId: res.data.orderId, state: "ACTIVE" });
               tx.set(db.doc(`players/${uid}`),
                 { hostEntitlement: true, updatedAt: FieldValue.serverTimestamp() },
                 { merge: true });
             });
             // 5. acknowledge（3 天内必须，否则 Google 自动退款）
             await publisher.purchases.products.acknowledge({
               packageName: PACKAGE, productId: "host_unlock", token: purchaseToken,
             });
             return { status: "granted" };
           });
          设计要点：①   幂等——purchaseToken   全局唯一，作为文档主键天然去重，重放安全；②   归属校验——
          obfuscatedAccountId 与 uid 强绑定，杜绝「拿别人的票据换权益」；③ 事务写入——票据与权益要么同时落库要么
          都不落，杜绝半状态；④ 服务端 acknowledge——绝不依赖客户端确认。
          11.3　RTDN 退款处理（M2 上线）
          Google Play 的退款 / 撤销通过 RTDN（Cloud Pub/Sub push 到云函数）推送：收到 ONE_TIME_PRODUCT_VOIDED → 按
          messageId 幂等 → 查票据文档取 uid → 事务回滚权益（hostEntitlement=false，票据 state=REFUNDED）→ 埋点
          entitlement_revoke。恶意退款玩家下次建房时被门禁拦截，UI   文案「订单已退款，房主资格已回收」。断网兜

          22.2　立项结论
            V7.0 总结论：建议立即立项，技术债清单清零
            三个版本的演进收敛为一个清晰命题：用 PC 端已验证的合作恐怖玩法，在 Android 空白市场，以 AI 主力生产
            和真·零成本技术栈，把 1 人团队的产能推到 2~3 人小队水平。V7.0 在 V6.0 十项改进之上，完成了三件决定
            生死的事：语音通道换轨 Vivox 使核心机制的商用许可归零（P0-A）；后端六能力补全使商业化与合规有了服
            务端地基（P0-B）；容量基线校准使免费档的每一条规则都被显式管理（P0-C / P1-D / P1-E / P1-F）。
            全部修正未增加任何现金成本（预算三档合计与 V5 持平，±1%），新增工期 ≈ 2.5 周且与既有里程碑并行。
            前端设计（V6 第四、五部分）经第三轮评审确认无恙，原样有效。M0 结束时，请带着双轮内测数据回到 V5 第
            3 章、V6 §4 与本方案 §3/§12——用真实世界的尖叫与数据，修订它们。
