# 实测 bug：`tools/fast-download.mjs` 的**并行模式会写坏数据**（2026-10-06）

## 现象
`kit-visibility` 任务明明 `success`，产物却解不开：
```
unzip: End-of-central-directory signature not found
```
而**文件大小与 GitHub 报的完全一致**：
```
本地文件:            1394103 字节
API size_in_bytes:   1394103
Content-Range 权威值: bytes 0-0/1394103
```
**⇒ 大小对、内容错** —— 典型的"数据被写到错误位置"。

## 定位
| 下载方式 | 结果 |
|---|---|
| `--conn 8`（并行分块） | ✗ ZIP 损坏 |
| **`--conn 1`（单连接）** | **✓ `unzip -t: No errors detected`** |

**⇒ bug 在我的并行实现里，不在 GitHub、不在网络。**

## 为什么"大小校验"没能拦住它
`fast-download.mjs` 的完成判据是 `done.size === NCHUNK && size === total` ——
**它只校验"每个块都写过了"，不校验"写的位置对不对、内容对不对"**。
一个块若把数据写到了偏移错误的位置，字节总数仍然正确，文件却已经坏了。

**⇒ 教训：字节数相等 ≠ 内容正确。** 这与本会话反复出现的"假绿"是同一类：
**判据覆盖不到真正的失效模式。**

## 处置
1. **暂缓并行模式**：本会话内涉及"必须完整"的产物（ZIP/APK）一律用 `--conn 1`。
   实测单连接 1.3 MB / 24 秒，对这类小产物完全够用（并行只在几十 MB 以上才值得）。
2. **并行模式待修**：需要加**写入位置的自校验**（例如每块写入前断言偏移 =
   `idx * CHUNK`，或整文件 CRC 与 Content-MD5 比对），修好前不给关键产物用。
3. 这类"大小对内容错"的失效**必须有一个内容级判据**（CRC / 解压测试）——
   已记入 `docs/`，作为后续加门禁的输入。
