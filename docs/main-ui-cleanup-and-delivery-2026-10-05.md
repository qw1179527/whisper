## 4. 本轮另一个重要发现（键盘从未真正生效过）

**现象**：`adb shell input keyevent KEYCODE_SPACE`（以及 H/J）在焦点正常、设备醒着时也毫无反应
（两次截图 SHA 完全相同）。

**根因（读码确认）**：键盘检查写在 `HandleBoardInput` 内部，而它在 `if (!clicked) return false;`
**之后** → **纯按键事件（没有任何触摸）永远走不到那些分支**。键盘只有恰好和一次点击同帧才生效。

**修法（本轮已改）**：新增 `HandleMenuKeyboard()`，在 `Update()` 里**每帧无条件**检查
（`GetKeyDown` 本身就是"这一帧按下"的语义）；`HandleSelfDrawClick()` 挪到 `_root/_paused` 早退**之后**。

> 这条同时解释了用户报的「菜单板选项点了没反应」的一部分成因：
> 输入处理被挂在"点到了某物"的条件链里，而不是独立、每帧、无条件地跑。

## 5. 真机取证的坑（已定位，供以后需要时用）

本会话在真机取证上烧掉大量轮次，根因已在第 10 轮定位清楚，记在这里避免重蹈：

| 坑 | 证据 | 处置 |
|---|---|---|
| 设备进入 **Dozing**（打盹）后应用失焦 | `dumpsys power` → `mWakefulness=Dozing`；`mCurrentFocus=NotificationShade` | 先 `svc power stayon true` + `settings put system screen_off_timeout 1800000`，再确认 `mCurrentFocus` 是应用才操作 |
| 通知栏抢焦点 | 同上 | `adb shell cmd statusbar collapse` + `KEYCODE_BACK`，**并复核焦点** |
| 截图二进制损坏 | `adb exec-out screencap -p > x.png` 会坏 | 用 `adb shell screencap -p /sdcard/x.png` + `adb pull` |
| "画面变了"不等于"业务接住了" | Tick 在涨 → 任何两次截图 SHA 必然不同 | 要读**业务回执**（HUD 行/logcat），不看像素差 |
| 画面逐帧 SHA 完全相同 | 大厅有灵球漂浮，不可能逐字节一样 | 这才是"渲染/主循环停了"的硬证据 |
